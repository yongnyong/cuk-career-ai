# 개인별 스킬트리와 추천 퀘스트 구현 계획

화면과 메뉴 이름은 **스킬트리**다. **추천 퀘스트**는 그 안에서 학생에게 다음 준비 노드를 추천하는 기능의 이름이다. 학생이 목표 직무를 고르면 학과·학년·보유 역량과 실제 공고 근거에 맞춰 기존 스킬트리 화면의 가지를 구성한다. 그 트리에서 지금 시작할 노드 하나에 **추천 퀘스트**를 표시한다. 학생은 기존처럼 노드를 눌러 무엇을 준비할지, 어떤 근거로 추천됐는지 확인한다.

## 2. 공고와 학과 자료를 스킬 근거로 바꾸기

- 입력은 현재 카탈로그, 학생 프로필, 실제 공고의 직무·필수·우대·최신 버전, `api/app/career/evidence.json`의 조건·활동·학과 자료다. 학점·수강 내역은 현재 웹 프로필에 없다. 이번 구현은 기존 입력만으로 작동하도록 한다.
- 근거 한 건에는 **어떤 스킬인지**, **어느 직무 또는 학과에 적용되는지**, **필수·우대·학과 권장·학습 활동 중 무엇인지**, **어디서 확인할지**가 있어야 한다. 공고는 공고 ID·버전·가능한 원문 문단과 링크, 자료집은 레코드 ID와 원문 링크를 보존한다. 시험 공식 사이트는 시험 안내 출처로만 쓴다.
- 구조화된 `skill` ID를 우선한다. 자료집의 자격명은 검증한 별칭으로 연결한다. SQL 사용 경험과 SQLD 취득은 다른 노드다. 활동도 무엇을 배우거나 수행하는지 근거가 있을 때만 연결한다. 매핑에 실패한 건은 건너뛴다. 동일 공고의 중복 수집본이나 과거 버전은 한 번만 센다.
- 실제 공고가 현재 지원 가능한지와 장기 준비에 참고할 수 있는지를 따로 판정한다. 예를 들어 졸업예정자 공고의 명시 역량은 2학년의 준비 근거가 될 수 있다. 기존 `recommend`·`evaluate`·`TreeNode.opportunities`는 계속 현재 기회 표시를 담당한다. 마감 사례에는 과거 공고임을 표시하고, 가상 공고는 실제 근거 수와 순위에서 제외한다.
- 어학 대체 조건은 기존 `assess_group`의 그룹 판정을 재사용한다. 한 가지로 충족했다면 그 공고를 근거로 다른 시험을 권하지 않는다. 점수·유효기간이 불명확하면 ‘기록 확인’으로 처리한다. 학과 권장 점수를 기업의 지원 하한으로 표시하지 않는다.

## 3. 알고리즘 A — 개인별 트리 구성

`web/src/lib/skillTree.ts`의 `buildPersonalizedTree`에 구현한다. 관리자 수정이 적용된 실제 직무 그래프를 입력으로 받아 `nodes`, `edges`, 스킬별 `evidenceRefs`를 산출한다. 입력과 기준 시각이 같으면 결과도 같아야 한다.

1. 선택한 직무의 필수 노드와 해당 트랙에서 학생이 이미 완료·인증한 노드를 먼저 담는다. 학과 전용 트랙은 소속과 공고 연결용 `base` 직무를 함께 확인한다. 학과와 다른 계열의 공통 직무를 선택한 학생도 그 선택을 존중한다.
2. 남은 선택 노드의 우선순위는 **직무에 직접 연결된 실제 근거 → 학년별 준비 단계와의 일치 → 서로 다른 근거 공고 수 → 템플릿 순서**로 정한다. 실제 근거 안에서는 명시 필수, 명시 우대, 출처 있는 학과 권장·활동을 구분한다. 저학년에게 졸업 학위 취득이나 지원 자체를 당장의 행동으로 고르지 않는다. 근거 없는 점수·준비 기간을 추정하지 않는다.
3. 첫 구현은 위 순서에서 근거가 있는 선택 노드를 최대 **2개** 포함한다. 이는 화면 복잡도를 조절하기 위한 초기값이며 필수 노드·완료 기록·선수 노드는 이 한도에서 제외한다. 해당 직무의 선택지를 가를 근거가 전혀 없으면 기존 템플릿 전체를 기본 경로로 사용한다. 근거가 비어 있다는 사실을 필수·우대의 증거로 해석하지 않는다.
4. 선택한 노드의 선수를 재귀적으로 포함하고 원본에 정의된 간선만 연결한다. 모든 간선의 양끝이 결과에 있어야 한다. 선수부터 위상을 계산하고 같은 깊이에서는 기존 순서로 배치한다. 첫 버전의 후보 범위는 선택한 직무의 유효한 카탈로그 노드다. 자료에만 있는 자격·활동은 원래 트리에 대응하는 노드가 생기기 전까지 신규 노드로 만들지 않는다.
5. 결과는 프로필 원본을 덮어쓰지 않는 파생 데이터로 취급한다. 예전 프로필도 첫 진입 시 계산한다. 근거 버전이 바뀌어 가지가 달라져도 해당 트랙의 완료 노드·증빙은 계속 보인다. 트리의 진행률 분모와 인쇄 화면은 같은 선택 노드 집합을 사용하고 기존 완료 상태의 경험치 계산은 유지한다.

## 4. 알고리즘 B — 추천 퀘스트 하나 선정

1. **이번에 구성한 그래프 안**에서 선수가 충족된 노드를 추린다. 일반 후보는 미완료 노드다. 이미 완료한 점수형 노드도 실제 유효한 목표와 기록을 비교해 미달이 확인되면 ‘점수 보완’ 후보가 될 수 있다. 이때 완료 표시·경험치·인증은 그대로 유지한다. 단위가 다르거나 기록이 불명확하면 점수 차이를 만들지 않는다.
2. 검증된 역량 조건이나 현재 참여할 수 있는 학습 활동과 직접 연결된 후보를 먼저 본다. 추천할 가지의 최종 노드가 잠겨 있으면 그 경로상 지금 할 수 있는 선수 노드에 준비 근거를 전달한다. 이때 상세 문구에 ‘X를 준비하기 위한 선수 단계’라고 표시한다. 공고에 그 선수까지 명시됐다고 쓰지 않는다.
3. 같은 우선순위에서는 학년 단계 일치, 트랙 필수 여부, 서로 다른 근거 공고 수, 원본 순서로 하나를 결정한다. 근거가 부족하면 시작 가능한 기본 경로 노드 하나를 ‘직무 기본 경로’로 표시한다. 후보가 없으면 `recommendedQuest = null`이다. 트리 전체 완료와 데이터 부족은 기존 빈 상태 문구에서도 구분한다.
4. 추천 결과는 `skillId`, `actionKind`(시작·보완·확인), `reasonCode`, `evidenceRefs`를 가진다. 노드에는 표시 하나, 기존 상세에는 이유 한 줄과 다음 준비 행동 한 줄을 넣는다. 원문이 있으면 기존 출처 영역에서 연다. 완료 상태·점수·직무·공고 근거가 바뀌면 다시 고른다. 날짜가 바뀌었다는 이유만으로 추천을 교체하지 않는다.

**구현 예시** · `data-analyst` 템플릿에는 `SK-SQL → SK-SQLD` 간선이 있다. 2학년 학생에게 SQL 기록이 없고, 테스트용 실제 형식 공고에 SQLD 우대가 명시됐다면 SQLD 가지와 그 선수 SQL을 포함한다. 다른 우선 근거가 없는 상황에서 추천 퀘스트는 SQL이다. 학생이 SQL을 완료하면 SQLD가 시작 가능한 후보가 된다. 공고가 SQL 사용 경험만 명시했다면 SQLD 우대로 연결하지 않는다. 이 예시는 구현 검증용이며 실제 공고 수집 결과를 주장하지 않는다.

## 5. 백엔드·모델·프론트 연결 순서

| 순서 | 작업 및 인터페이스 | 단계별 완료 기준 |
| --- | --- | --- |
| 1 | `api/app/career/`의 기존 판정을 재사용해 `POST /api/preparation/tree-signals`를 추가한다. 입력은 학과·학년·직무와 판정에 필요한 역량·점수, 출력은 카탈로그 스킬 ID에 연결된 `signals[]`와 자료 버전이다. 실제 웹 공고는 이미 로드한 `Opportunity[]`에서 같은 형식으로 결합하고 출처 ID로 중복 제거한다. | 웹 DB에 실제 공고가 없어도 저장된 근거로 작동한다. 서버 스냅샷에 없는 관리자 트랙은 웹의 유효한 그래프로 진행할 수 있다. |
| 2 | 실제 카탈로그와 근거를 받아 알고리즘 A와 B를 순수 함수로 구현한다. 웹의 공통 상태 계층에 결과를 공유한다. 프로필·카탈로그 버전·근거 버전·공고 버전·기준 시각의 모집 상태 변경을 반영한다. | 기존·신규 프로필이 같은 입력으로 같은 그래프와 추천을 얻는다. API 지연·실패 시에도 로컬 카탈로그와 가용 공고로 즉시 트리를 열 수 있다. |
| 3 | `/tree`의 `PreparationPanel` 연결을 제거한다. `NodeBox`에 선택적 추천 표시를 전달하고, 기존 상세에 행동과 근거를 붙인다. 홈의 ‘다음에 깰 노드’와 트리 사이드바의 ‘추천 퀘스트’ 행도 공유 결과를 읽게 한다. 인쇄와 프로필의 진행률도 확인한다. 온보딩·공고 목록·공고 상세의 레이아웃은 기존 흐름을 따른다. | 학생이 트리를 열면 별도 버튼 없이 한 노드에 추천 표시가 보인다. 그 노드를 누르는 기존 동작으로 설명을 볼 수 있다. 지원 체크리스트와 증빙 업로드가 정상 동작한다. |
| 4 | 추천된 노드의 기존 상세를 열 때 `POST /api/preparation/quest-action`으로 다음 준비 행동을 구체화한다. 기존 `ai_provider.generate_json`과 `require_local_ai`를 재사용한다. Codex에는 학년 단계·시간 범위·선정 노드와 허용된 행동/근거 ID를 주고 행동 하나를 고르게 한다. 문구의 수치·출처·자격명은 검증된 데이터로 렌더링한다. | 트리 구성·퀘스트 표시는 모델을 기다리지 않는다. 모델이 늦거나 허용되지 않은 행동·근거를 반환해도 규칙 기반 행동이 보인다. 별도 모델 창이나 API 키 입력이 필요하지 않다. |
| 5 | 같은 학생·입력·노드의 요청은 화면 세션에서 재사용하고 진행 중 중복 호출을 합친다. 완료 처리·직무 변경·로그아웃 시 이전 결과를 폐기한다. `nowDate`의 모의 시간도 입력으로 사용한다. | 홈 왕복·리렌더링만으로 Codex 호출이 반복되지 않는다. 다른 프로필의 결과나 늦게 도착한 예전 추천이 표시되지 않는다. |

로그인된 Codex CLI는 로컬 PC에서 호출하며 모델 추론은 계정 서비스를 사용한다. 학생 식별자·학번·성적표·증빙 파일·원점수는 모델 입력에서 제외한다. 원점수가 필요한 임계값 비교는 앱 코드가 수행한다. 기존 `/api/preparation/plan`과 `/api/chat` 호출 규약은 유지한다.

## 7. 완료 판정

| 검증 상황 | 기대 결과 |
| --- | --- |
| 같은 학과·직무, 서로 다른 2개의 실제 형식 공고 묶음 | 선택 가지 또는 추천 선수가 입력 근거에 맞춰 달라진다. 테스트는 바뀐 스킬 ID·간선·참조 공고 ID까지 비교한다. |
| 2학년과 졸업예정자, 같은 졸업예정자 공고 | 2학년은 역량 준비 이유를 볼 수 있고 현재 지원 가능 목록에는 공고가 잘못 추가되지 않는다. |
| SQLD 노드는 잠겨 있고 SQL 미완료 → SQL 완료 | 처음에는 시작 가능한 선수에 표시된다. 완료 후 새 후보를 계산한다. 이미 기록한 완료·증빙은 보존된다. |
| 어학 점수 미달·목표 달성·기록 불명·다른 시험으로 대체 충족 | 보완·종료·확인을 구분한다. 대체 충족한 공고를 근거로 이중 준비를 권하지 않는다. |
| 공고가 전부 마감·가상·중복이거나 실제 웹 공고가 0건 | 각 출처의 성격이 정확히 표시된다. 가상·중복 공고가 시장 근거로 집계되지 않는다. |
| 학과 전용 트랙, 공통 직무, 관리자 수정, 전체 완료, 예전 프로필 | 그래프의 모든 ID가 실제 카탈로그에 있고 간선의 양끝이 존재하며 순환이 없다. 전체 완료·보완 후보 없음이면 추천 표시가 0개다. |
| 모델 비활성·시간 초과·잘못된 응답, 직무 변경 중 늦은 응답 | 트리가 작동하고 표시와 상세가 항상 같은 노드를 가리킨다. |
| 동일 입력으로 홈 → 트리 → 추천 노드 상세 → 완료 → 인쇄 | 홈·사이드바·트리의 추천이 일치한다. 추천 표시는 최대 1개이며 진행률·인쇄 내역·기존 지원 체크리스트가 기대대로 유지된다. |

구현 후 `api`에서 `.\.venv\Scripts\python.exe -m pytest -q`, `web`에서 기존 Next 타입 생성·TypeScript 검사·ESLint를 실행한다. 그래프와 순위는 모델 호출 없는 고정 입력 테스트로 검증하고, 모델 연결은 가상 학생 한 명의 실제 HTTP 요청으로 별도 확인한다. 마지막으로 브라우저에서 위 사용자 흐름을 검증한 뒤 **통과한 범위와 실행하지 못한 범위**를 구분해 기록한다.

**다음 모델의 첫 작업** · 기존 미커밋 변경을 확인한 뒤 1단계의 스킬 근거 매핑과 2단계의 SQL 선수 사례부터 구현한다. 이 사례가 입력에서 개인별 그래프·퀘스트 ID까지 통과하면 기존 화면과 Codex 행동 설명을 연결한다.
