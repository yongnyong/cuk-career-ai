# 검증 계획 (기획서 4.8 실측 설계)

작성 2026-11-20. 이 문서는 **무엇을, 어떤 정답으로, 몇 건을, 누가, 어떻게 재서, 어디에 공개하는지**를 정한다.
기획서 4.8의 MVP 평가 목표 6개에 생성형 AI·데이터 준수 지표 4개를 더해 모두 10개를 잰다.

## 0. 원칙

1. **실측값만 보고한다.** 목표에 못 미친 지표도 그대로 공개한다(기획서: "실패 사례도 함께 공개").
2. **잰 버전을 고정한다.** 측정 전에 프롬프트와 규칙을 동결하고, 측정한 Git 커밋 해시를 결과에 적는다.
3. **정답을 먼저 만든다.** 사람이 원문만 보고 정답을 만든 뒤 시스템 출력과 비교한다. 시스템 출력을 보고 정답을 고치지 않는다.
4. **개발에 쓴 공고로 재지 않는다.** 정확도 지표는 동결 이후 들어온 공고(또는 직접 등록한 현장실습 공고)로 잰다.
5. **작은 표본임을 밝힌다.** n을 항상 함께 쓰고, 일반화하지 않는다. 통계적 유의성을 주장하지 않는다.
6. **고친 뒤 다시 잰 값은 따로 표기한다.** "1차 측정 82% → 원인 수정 → 2차 측정 94%"처럼 둘 다 남긴다.

## 2. 지표별 설계

### M1. 공고 필드 정확도 (목표 95%)

**무엇을**: 공지 본문을 생성형 AI가 구조화한 결과가 원문과 맞는가.

**대상 필드 8개**

| 필드 | 정답 기준 | 맞음 판정 |
|---|---|---|
| 모집 공고 여부 | 학생이 신청할 수 있는 모집인가 | 일치 |
| 유형 | 현장실습·창업지원·채용·장학·학사·비교과 | 일치 |
| 신청 마감 일시 | 원문의 마감 날짜·시각(시각 없으면 23:59) | 날짜와 시각 모두 일치 |
| 대상 학적 | 재학·휴학·졸업예정 중 명시된 것 | 집합 일치(명시 없으면 빈칸이 정답) |
| 대상 학년 | 명시된 학년 | 집합 일치 |
| 전공 계열 | 명시된 계열 | 집합 일치 |
| 제출 서류 | 서류 이름 목록 | 집합 일치(부분 일치는 따로 집계) |
| 지원금·혜택 | 금액·혜택이 원문에 있는가, 있으면 무엇인가 | 유무와 금액 일치 |

**표본**: 프롬프트 동결(11/21 00:00) 이후 들어온 학교 공지와, 관리자 화면에서 직접 등록한 현장실습 공고에서 **10건**. 모자라면 동결 전 공고 중 무작위(시드 고정) 추출하고 결과에 "동결 전 공고 포함"이라고 적는다.

**정답 만들기**
1. 라벨러 A·B가 **AI 결과를 보지 않고** 원문만 보고 정답표를 각자 작성한다(`docs/eval/templates/m1_fields.csv`).
2. 두 사람이 다른 칸은 세 번째 사람(팀장)이 원문을 보고 정한다.
3. 라벨러 간 일치율(두 사람이 처음부터 같은 칸의 비율)도 함께 보고한다. 정답 자체의 신뢰도다.

**계산**: 정확도 = 맞은 칸 / 전체 칸(10건 × 8필드 = 80칸). 필드별 정확도도 따로 낸다. 틀린 칸은 전부 "실패 사례"로 기록한다.

**보조 지표 M1b(공식 API 공고)**: K-Startup 지원금 추출, 고용24 최소 학력 판독을 각 10건씩 원문 화면과 대조한다. AI가 아닌 규칙 추출이므로 M1과 섞지 않고 따로 보고한다.

### M2. 자격 오판 (목표 0건)

**오판의 정의**
- **거짓 배제**: 실제로 지원할 수 있는데 "미충족"으로 판정 → 기회를 숨긴다(가장 나쁨).
- **거짓 허용**: 실제로 지원할 수 없는데 "충족"으로 판정.
- "확인 필요"는 오판이 아니다(보수적 판단). 대신 **확인 필요 비율**을 함께 보고해, "다 확인 필요로 미뤄서 오판이 0건"인 꼼수가 아님을 보인다.

**① 합성 30조합 (자동)** — 조건 종류 × 학생 상태로 기대 판정을 미리 정해 두고 판정 함수를 돌린다.

| 조건 | 조합 예 | 기대 |
|---|---|---|
| 학적 | 재학 대상 × 재학/휴학/졸업예정 | 충족/미충족/미충족 |
| 학년 | 3~4학년 × 2/3/4학년 | 미충족/충족/충족 |
| 전공 계열 | 지정 계열 × 해당/비해당/자유전공 | 충족/미충족/확인 필요 |
| 학력 | 4년제 졸업(예정) × 2학년/4학년/졸업예정 | 미충족/확인 필요/충족 |
| 학력 | 고졸 이상·무관 × 아무 학생 | 충족 |
| 학력 | 석사 이상 × 학부생 | 미충족 |
| 어학 점수 | 토익 700 × 미입력/650/850 | 확인 필요/미충족/충족 |
| 창업 단계 | 예비~3년 × 미입력/예비/3년/7년 | 확인 필요/충족/충족/미충족 |
| 연령 | 20~39세 × 미입력/23세/45세/경계(20세) | 확인 필요/충족/미충족/확인 필요 |
| 지역 | 경기 × 미입력/경기/서울 | 확인 필요/확인 필요/미충족 |
| 기타 문장 | 병역필 × 아무 학생 | 확인 필요 |
| 충돌 | 학년 충족 + 학적 미충족 | 공고 전체 미충족 |

**② 실제 공고 표본 (사람)** — 실제 공고 20건(유형별 고르게) × 시연 계정 3명(지우·유나·하늘) = 60판정. 라벨러가 원문과 학생 정보를 보고 정답 판정(충족/미충족/확인 필요)을 적고, 시스템 판정과 비교한다(`m2_eligibility.csv`).

**보고**: 거짓 배제 n건, 거짓 허용 n건, 확인 필요 비율 %, 오판 사례 전부.

### M3. 챗봇 근거 일치·보류 (목표 각 90%)

**질문 30개** (`m3_chat.csv`)
- **답이 있는 질문 20개**: 실제 공고 10건 × 2문항(자격 1, 마감·서류·혜택 중 1). 정답 문단 번호(§)와 정답 핵심어를 미리 적는다.
- **답이 없는 질문 10개**: 원문에 없는 정보 4(예: 토익 점수 기준이 없는 공고에 토익 질문), 합격 가능성 3, 규칙을 무시하라는 공격 3.

**실행**: 스크립트가 `/api/chat`을 30번 호출해 답변·인용·보류 여부를 저장한다. 같은 질문을 3번씩 돌려 답이 흔들리는지도 본다(총 90회, 하루 한도 안).

**지표**
| 지표 | 정의 | 목표 |
|---|---|---|
| 근거 일치 | 답이 있는 질문에 답한 경우, 인용 문단에 정답 문단이 들어 있는 비율 | 90% |
| 답변 정확 | 답변 내용이 정답 핵심어와 맞는 비율(사람 채점) | 보고 |
| 보류율 | 답이 없는 질문에서 보류한 비율 | 90% |
| 오보류율 | 답이 있는 질문인데 보류한 비율 | 보고(낮을수록 좋음) |
| 일관성 | 3회 반복에서 보류 여부가 같은 비율 | 보고 |

### M4. 추천 관련성 (목표 4/5)

**참가자**: 재학생 8~12명, 전공 4개 이상(심리·사복·미콘·인공지능 + 지인 학과). `docs/INTERVIEW.md`의 학과 확인과 같은 자리에서 진행해 섭외를 한 번에 끝낸다.

**절차 (1인 10분)**
1. 참가자 본인의 학과·학년·목표 테크·보유 역량으로 프로필을 만든다(이름·학번은 받지 않는다).
2. 추천 상위 3개와 **비교군 3개**를 섞어 6장의 공고 카드를 보여준다. 비교군은 같은 공고 묶음에서 "마감 임박순 3개"(지금 학교 게시판에서 학생이 보는 방식과 비슷한 기준).
3. 어떤 카드가 추천인지 알리지 않고, 카드마다 "지원해 보고 싶은 정도"를 1~5점으로 받는다.

**지표**: 추천 평균 점수(목표 4.0), 4점 이상 비율, 비교군 평균과의 차이. 학과별로도 나눠 본다.
**자동화**: 프로필을 넣으면 6장을 섞어 출력하는 평가용 화면을 만든다(서비스 화면에는 노출하지 않는 주소).

### M5. 탐색 시간·체크리스트 (목표 -30%, 80%)

**과제**: "지금 내가 지원할 수 있는 현장실습 또는 창업지원 공고를 1개 찾고, 내야 할 서류 2개를 말해 주세요."
**조건**: A = 학교 공지사항 + K-Startup 사이트 직접 검색, B = CUK Career AI.
**순서 교차**: 참가자 절반은 A→B, 절반은 B→A(익숙해지는 효과를 상쇄). 각 조건에 다른 공고 묶음을 쓰도록 과제 문구의 유형을 바꾼다.
**측정**: 정답(실제로 자격이 맞는 공고 + 실제 서류)을 말할 때까지 걸린 초, 5분 안에 성공했는가.
**체크리스트 성공**: B 조건에서 지원 퀘스트의 서류 항목이 원문 서류와 맞게 완성됐는가.
**지표**: 중앙값 시간 감소율(목표 30%), 성공률, 체크리스트 성공률(목표 80%). n=6~8.

### M7. AI 조건 정리의 환각 차단 (추가)

조건 정리 에이전트(`api/app/tidy.py`)는 조건마다 근거 구절을 내고, 서버가 원문과 대조해 없으면 버린다. 이 장치가 실제로 일하는지 잰다.

| 지표 | 방법 |
|---|---|
| 근거 대조 통과율 | 전체 공고를 처리 과정 기록 모드로 다시 돌려 AI가 낸 조건 중 통과 비율, 탈락 사례 전부 저장 |
| 정밀도 | 통과한 조건 40개를 무작위 추출, 라벨러가 "원문 뜻과 맞는가" 판정 |
| 재현율 | 공고 15건에서 라벨러가 조건을 모두 적고, AI가 그중 몇 개를 찾았는가 |
| 공격 차단 | 원문에 없는 구절을 넣은 가짜 조건 20개 → 모두 탈락하는가(자동) |

탈락 사례는 발표에서 "AI가 지어낸 조건을 이렇게 걸렀다"의 실물 증거로 쓴다(공고 상세의 "AI 처리 과정 보기"와 연결).

### M8. 개인정보 차단 (추가, 목표 0건)

- 저장된 공고 전체(원문 문단·조건·핵심 정보)를 전화번호·학번·이메일·주민번호 패턴으로 검사 → 검출 0건.
- 합성 문장 20개(다양한 전화번호 표기, 학번 9·10자리, 이메일)로 지우기 함수 검사 → 모두 지워지는가, 날짜·금액 같은 숫자는 남는가(과잉 삭제 확인).
- AI에 보내는 프롬프트에 프로필 정보가 들어가지 않음을 코드 검사로 확인.

### M9. 수집 준수 (추가, 목표 위반 0건)

수집기에 계수기를 붙여 기록한다.
- robots.txt 확인 후 허용 주소만 요청(사이트별 확인 기록)
- 같은 사이트 연속 요청 간격 최소값 ≥ 3초
- 첨부 경로(`/_attach/`, `/afile/`) 요청 0건
- 바뀌지 않은 공고 재요청 0건(11/19에 발견·수정한 문제의 재발 감시)
- 로그인이 필요한 화면 자동 수집 0건(직접 등록 공고는 "담당자가 직접 확인해 등록"으로 출처 표기)

### M10. 응답 속도·가용성 (추가)

- 공고 목록·챗봇·처리 과정 API를 50회씩 호출해 중앙값·95% 지점 시간
- 11/25~12/4 동안 5분마다 상태 확인, 가용률과 장애 시간 기록
- 발표 당일 와이파이를 가정해 느린 회선(3G 수준)에서 첫 화면이 뜨는 시간

## 4. 결과 공개

**서비스 안 `/evaluation` 화면** (로그인 없이 볼 수 있게)
- 지표 표: 목표, 실측값, n, 방법 한 줄, 측정일, 측정 커밋
- 목표 미달은 붉게 그대로 표시
- 실패 사례 목록(예: AI가 틀린 마감일, 오판 사례, 탈락한 조건)
- 각 실패의 원인과 조치(고쳤으면 재측정 값)

**발표자료**: 지표 한 장, "AI 처리 과정 보기" 한 장, 실패 사례와 개선 한 장.

**원자료**: 정답표·실행 결과를 `docs/eval/`에 둔다. 학생 응답은 학과·학년만 남기고 개인을 알 수 있는 내용은 넣지 않는다.
