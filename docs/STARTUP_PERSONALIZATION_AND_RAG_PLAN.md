# 창업 대화형 온보딩과 공고 추천 RAG 구현 계획

구현 순서는 **A. 창업 개인화 → B. 취업·창업 공고 검색과 근거 설명**이다. A의 시연은 검색 인덱스나 외부 공고 추가 수집 없이 완성한다. B는 A에서 얻은 고객·아이디어·목표를 검색에 사용한다.

기준 코드는 2026-11-23에 확인한 로컬 통합 커밋 `d5cf2fe`다. 여기에는 당시 원격 main `63b410b`의 개인 진로 비서·노드 질문 기능과 PR #3의 스킬트리 변경이 함께 있다. 작업 시작 시 두 기능이 모두 있는 체크아웃을 확인한다. 이 문서는 설계 인계본이며 두 기능의 구현 상태를 뜻하지 않는다.

## A. 가입 직후 대화가 창업 퀘스트로 이어지게 한다

### 학생이 경험할 흐름

1. 기존 방식으로 가입하고 취업·창업 관심을 선택한다. 창업 선택자는 학과·학년 등 기본 정보를 입력한 뒤 **같은 온보딩 화면 안에서 기존 비서와 대화**한다. 기존 ‘보유 역량 진단’과 창업 목표 선택이 이 대화로 이어진다. 이미 답한 정보는 다시 묻지 않는다. 취업 온보딩은 기존 경로를 사용한다.
2. 첫 질문은 “누가 어떤 상황에서 쓸 제품이나 서비스를 만들고 있어요?”다. 답에서 **아이디어, 고객, 이미 해본 일·보유 결과물, 가까운 목표**를 추출한다. 정보가 충분하면 한 번 만에 추천한다. 부족하면 다음 추천을 실제로 바꿀 질문을 한 번씩, 최초 흐름에서 최대 두 번 더 묻는다. 빠른 답변으로 ‘첫 고객 만나기’, ‘제품 출시’, ‘대회·지원사업 신청’을 제공한다.
3. 이해한 내용을 짧게 보여주고 학생이 직접 수정할 수 있게 한다. ‘내 스킬트리 보기’는 기존 `/tree`를 연다. ‘나중에 답하기’를 선택하면 공통 준비를 보여주고 다음 방문 때 이어간다. 첫 버전의 소유 단위는 학생 계정 하나와 창업 아이디어 하나다.
4. 창업 트리는 **공통 준비 / 우리 팀 맞춤** 두 탭을 쓴다. 맞춤 정보가 충분하면 개인 탭에서 추천 퀘스트 하나를 먼저 보여준다. 노드 상세에는 ‘추천 이유, 해야 할 일, 완료 결과물, 관련 근거’를 표시한다. ‘이 노드 AI에게 물어보기’도 같은 결과물을 설명해야 한다.

### A1. 추천 규칙과 기준 사례부터 만든다

새 백엔드 모듈 후보는 `api/app/assistant/startup_plan.py`다. 먼저 네트워크 호출 없이 창업 프로필과 선택 공고를 받아 개인 노드를 만드는 함수를 구현한다. 두 학생의 이름이나 특정 기업명을 조건문에 넣지 않는다.

| 항목 | 구현 결정 |
|---|---|
| 입력 | 학생이 말한 아이디어·고객·결과물·목표를 저장한다. ‘현 사업 등록 상태·업력’과 ‘과거 창업·폐업 경험’을 별도로 다룬다. 기존 프로필의 단계는 재사용한다. 미응답은 ‘모름’으로 두고 현재 온보딩의 자동 `pre` 기본값도 점검한다. 사업자등록·재창업 이력은 추천 또는 공고 판정을 바꿀 때만 묻는다. |
| 공통 준비 | 기존 카탈로그의 결과물 중 팀이 재사용할 수 있는 것부터 선별한다. ‘피치덱’은 학생 화면에서 ‘아이템 소개 발표자료’로 표시한다. 기존 노드 ID를 유지해 완료 이력을 연결한다. |
| 개인 노드 생성 | 목표에 필요한 행동을 고른 뒤 고객·제품·보유 결과물로 제목과 완료 기준을 구체화한다. 예를 들어 같은 ‘고객 시연’이라도 학원장에게는 수정 가능한 상담 요약 화면, 매장 관리자에게는 해당 매장 업무의 시연 결과물이 된다. AI는 허용된 행동을 구체화할 수 있다. 필수 서류·신청 자격은 확인된 원문에서만 가져온다. |
| 우선순위 | 완료한 일을 제외하고, 가까운 목표에 직접 필요한 일과 현재 결과물로 시작할 수 있는 일을 먼저 추천한다. 최초 화면은 첫 추천 1개와 필요할 때 후속 후보 최대 2개를 기본값으로 삼는다. 후보가 적으면 그대로 보여준다. |
| 연결과 갱신 | 앞 결과물을 다음 과제에 실제로 쓸 때 연결한다. 각 노드에는 안정적인 ID, 행동 종류, 제목, 완료 기준, 추천 이유, 상태, 선택적 근거를 둔다. 제목 수정·새로고침·재시도로 ID가 바뀌지 않아야 한다. 목표 변경 시 영향받는 미완료 노드만 갱신하고, 완료한 작업은 당시 제목·결과물과 함께 보존하여 재사용한다. |
| 근거 | 서비스 제안과 공고 명시 요건을 구분한다. 후자에는 공고 ID, 버전, 원문 인용과 링크를 붙인다. ‘사업자등록증 제출’은 특정 공고의 서류 과제다. 모든 예비팀에 등록이나 통신판매업 신고를 선행 과제로 배정하지 않는다. |

### A2. 기존 비서·저장소·온보딩을 연결한다

| 작업 위치 | 변경 내용 |
|---|---|
| [비서 데이터 계약](../api/app/assistant/contracts.py), [대화 처리](../api/app/assistant/service.py) | 기존 대화 요청에 선택적인 창업 온보딩 목적을 추가하고, 같은 대화 이력을 사용한다. 구조화된 응답에서 명시된 필드만 부분 갱신한다. 기존 비서 모델 인터페이스를 재사용한다. 대화가 실패하거나 구조화 결과가 유효하지 않으면 이전 값을 보존하고 빠른 선택지로 진행한다. 일반 질문·가정·다른 팀 이야기를 학생 자신의 목표 변경으로 저장하지 않는다. |
| [비서 저장소](../api/app/assistant/service_data.py), [비서 라우터](../api/app/assistant/router.py) | 사용자별 `UserState`에 선택적 `startup_plan`을 두고, 새 프로필 정보와 개인 노드의 원본으로 삼는다. 기존 상태 JSON도 읽어야 한다. 로그인 계정은 기존 영속 저장소, 데모는 기존 쿠키로 분리된 데모 저장소를 따른다. 읽기·정정·개인 노드 완료에 필요한 최소 API를 같은 인증 경계에 둔다. 기존 대화 요청 ID와 저장 버전을 이용해 중복 요청과 여러 창의 동시 수정을 처리한다. |
| [온보딩](../web/src/app/onboarding/page.tsx), [기존 챗봇](../web/src/components/Assistant.tsx) | 창업일 때 같은 채팅 컴포넌트와 비서 컨텍스트를 온보딩 본문에 표시한다. 이때 떠 있는 챗봇 버튼과 입력창이 중복되지 않게 한다. 현재 프로필은 `finish()`에서 저장되므로, 가입 세션과 입력 중인 창업 관심 정보만으로 첫 대화를 시작할 수 있어야 한다. 중도 이탈 후 재진입과 건너뛰기도 확인한다. |
| [웹 상태](../web/src/lib/store.tsx), [타입](../web/src/lib/types.ts) | 응답의 `startupPlanUpdated` 신호로 최신 창업 계획을 읽고, 창 재활성화·계정 변경 시 상태를 맞춘다. 이미 열려 있는 화면에서도 다음 추천이 바뀌어야 한다. 개인 계획은 현재의 프로필 전체 저장 `PUT /api/me/state`와 이중 저장하지 않는다. 공통 노드의 기존 완료 상태는 `profile.skills`, 개인 노드 완료는 소유자별 계획에서 읽는다. 계정 전환 시 이전 캐시를 비운다. |

**권장 API 계약.** 대화는 기존 `POST /api/assistant/chat`에 선택적인 `mode=startup_intake`를 추가해 처리한다. 기존 호출자는 지금처럼 모드 없이 호출한다. `GET /api/assistant/startup-plan`은 본인의 요약·활성 노드·보존된 완료 노드·버전을 돌려준다. `PATCH /api/assistant/startup-plan`은 화면에서 직접 정정한 필드나 노드 완료 변경과 읽었던 버전을 받는다. 서버는 허용 필드와 본인 소유 노드를 확인한다. 중복 완료는 한 번만 적용하고, 버전 충돌 시 최신 계획을 읽어 해당 변경만 다시 적용한다. 학생이 모른다고 한 값, 답하지 않은 값, 기존 답을 취소한 경우를 구분한다.

### A3. 기존 트리에 표시하고 개인 노드에서 다시 질문한다

[창업 트리 생성](../web/src/lib/startup.ts)에 개인 계획을 입력으로 추가한다. [배치](../web/src/lib/treeProgression.ts), [퀘스트 결과물](../web/src/lib/questOutcome.ts), [스킬트리 화면](../web/src/app/tree/page.tsx)에서 공통·맞춤 탭과 탭 사이의 결과물 연결을 표시한다. 현재 창업 분기는 모든 노드를 한 목록으로 보여주므로 탭 라벨뿐 아니라 후보 선택과 첫 추천도 바꿔야 한다. 정보가 부족하거나 서버가 잠시 응답하지 않으면 기존 공통 경로 또는 마지막으로 읽은 개인 계획을 보여준다.

현재 노드 질문 기능은 기본 직무 카탈로그에 없는 노드의 이름만 보낸다. 개인 노드는 별도 식별자를 받아 서버에서 **현재 사용자 계획의 노드**를 조회한다. ‘어떻게 준비해?’에 이 학생의 결과물·완료 기준·선택 공고로 답하도록 한다. 개인 노드를 전역 공고 DB나 모든 사용자용 스킬 카탈로그에 등록하지 않는다.

### A 완료 검수

| 동일 조건에서 바꿀 입력 | 기대 결과 |
|---|---|
| 경영학과 4학년, “동아리 굿즈 디자인이 있고 첫 온라인 선주문을 받아보고 싶어” | ‘첫 선주문 상품 페이지 초안’이 첫 추천. 기존 도안, 수량별 가격, 수령 방식을 반영한 편집 가능한 페이지가 남는다. |
| 같은 학과·학년, “학원 상담 요약 AI 시제품이 있고 다음 주 원장님에게 보여줘” | ‘학원장 미팅용 상담 요약 시연본’이 첫 추천. 가상 입력, 요약 결과, 수정 화면이 완료 기준에 들어간다. 시제품을 다시 만들라는 과제가 앞에 오지 않는다. |
| 두 번째 팀이 시연본을 완료하고 홈에서 “이제 교내 창업대회에 낼래”라고 말함 | 완료한 시연본 ID와 기록이 남는다. 대회가 정해지기 전에는 지원 후보를 확인하고, 선택 후에 해당 공고의 규격에 맞춘 발표자료가 추천된다. 원문에 없는 규격은 추가하지 않는다. |
| 미응답·중도 이탈·모델 장애·예전 프로필·창 두 개·계정 전환 | 기본 화면에 진입 가능. 재시도로 노드가 중복되지 않으며 최근 목표와 완료 기록을 유지한다. 다른 학생의 아이디어가 노출되지 않는다. 데모의 서버 재시작 시 동작은 기존 데모 저장 정책을 따른다. |

우선 위 사례를 규칙 단위 테스트로 고정하고, 비서 모의 모델 통합 테스트와 가입 → 대화 → 트리 → 완료 → 목표 변경 브라우저 시연을 통과시킨다. 취업 가입·공고 추천과 기존 창업 카탈로그 테스트도 함께 돌린다.

## B. 취업·창업 공고에 공통 검색과 RAG를 적용한다

**검색은 순위를 바꾸고, 생성은 그 이유를 설명한다.** 구현과 평가를 따로 진행한다. [현행 추천 함수](../web/src/lib/engine.ts)의 지원 자격 판정과 취업의 명시적 직무·전공 신호를 기준선으로 보존한다.

| 순서 | 구현할 내용 | 확인할 결과 |
|---|---|---|
| B1. 기준선 고정 | 고정 공고 스냅샷과 기준일을 사용해 현행 추천을 기록한다. 취업 질의에는 목표 직무·업무·역량을, 창업 질의에는 A의 아이디어·고객·현재 목표를 사용한다. 분야별 질의에 검토자가 적합 공고와 근거 문단을 먼저 표시한다. | 새 검색을 켜기 전후에 동일한 모집 상태·프로필·자료로 비교할 수 있다. |
| B2. 검색용 문단 준비 | [공고 저장 모델](../api/app/career_db.py)의 최신 공고에서 제목, 담당 업무·지원 내용, 요건·우대, 제출물 문단을 나눈다. 공고 ID·버전·문단 ID·출처 URL·본문 해시를 유지한다. 과거 공고는 준비 참고 용도로 구분한다. 일반 공고 목록과 창업 게시 과정의 중복은 공고 단위로 제거한다. | 초기 일괄 색인, 변경분 반영, 재실행, 정정·삭제 시 이전 문단 제외가 가능하다. 색인은 공개 공고만 대상으로 한다. |
| B3. 후보 검색과 순위 | 새 모듈 후보는 `api/app/career/opportunity_search.py`다. 먼저 키워드 기준선을 만들고, 같은 API에서 키워드와 임베딩 순위를 합친 결과를 비교한다. 취업·창업을 먼저 구분하고 **기존 상위 8개로 제한하기 전에** 전체 해당 분야 공고에서 찾는다. 직무 분류가 비어도 업무 원문이 관련된 공고를 탐색 후보로 허용한다. | 특정 자격증 이름과 자연어 표현을 모두 찾는다. 의미 유사성으로 ‘관련 전공 우대’가 ‘전공 필수’가 되지 않는다. |
| B4. 한 목록을 웹·챗봇이 공유 | 검색 API는 후보 ID·순위·문단 근거를 반환한다. 현행 모집·자격 판정으로 제외된 행을 보충할 수 있게 후보를 충분히 가져오거나 다음 후보를 이어 읽는다. 웹 상태에서 최종 추천을 한 번 계산해 [공고 화면](../web/src/app/opportunities/page.tsx)과 [비서](../web/src/components/Assistant.tsx)가 공유한다. 관련 결과가 0건인 경우와 검색 실패를 구분하고, 실패 때 기존 규칙 결과를 사용한다. | ‘지원 가능 / 확인 필요’가 보존되고 명백한 자격 미달은 지원 추천에서 제외된다. 비서가 빈 후보 목록을 받은 상황에서 무관한 전체 목록으로 확대하지 않는지도 확인한다. |
| B5. 근거 있는 설명 | 상위 공고 또는 ‘추천 이유’ 요청에만 원문 문단을 넣어 ‘목표와 맞는 점 / 확인할 조건 / 원문’을 생성한다. 서버가 공고·버전·인용을 대조한다. 과거·다른 공고에서 가져온 문구, 근거 없는 필수 조건은 표시하지 않는다. 모델 장애 시에도 목록·원문은 볼 수 있다. | ‘SQL 활용 우대’는 공고 근거로, ‘SQLD 준비’는 서비스의 별도 제안으로 구분된다. |

운영 PostgreSQL 이미지는 pgvector를 포함한다. B 착수 시 실제 확장 활성화와 스키마 변경 절차를 점검한다. 개발용 SQLite에서도 같은 문단 ID와 키워드 기준선으로 테스트하고, 벡터 검색은 PostgreSQL 통합 테스트로 검증한다. 모델명·버전과 벡터 차원을 색인에 기록해 교체와 재색인이 가능하게 한다. 개인의 이름·학번·전체 대화는 공고 색인이나 임베딩 입력에 포함하지 않는다.

**첫 검색 구현의 기본값.** 취업은 ‘목표 직무·업무·역량’, 창업은 ‘아이디어·고객·이번 목표’로 짧은 질의를 만든다. 정확한 자격명·약어의 키워드 검색 순위와 업무·지원 내용의 의미 검색 순위를 RRF(각 순위의 역수를 합산하는 방법)로 결합해 시작한다. 같은 공고의 여러 문단은 공고 점수 한 개와 근거 문단 목록으로 합친다. 검색 API의 공통 결과는 `postingId, version, sectionId, quote, sourceUrl`을 포함한다. 지원 가능 여부는 기존 규칙의 판정 결과로 표시한다. 공고 버전 변경 시 해당 문단만 다시 임베딩하고, 목록 열람 때마다 LLM을 호출하지 않는다.

데이터 배포도 별도로 확인한다. 현재 취업 가져오기는 SQLite 파일에 쓰고 창업 공고는 별도 게시 경로를 쓴다. 테스트에서 사용한 공고·근거가 운영에도 존재하는지 공개 ID·버전으로 비교한다. 필요한 공개 공고만 반복 실행 가능한 적재로 보완하며, 코드 푸시가 로컬 DB를 복제한다고 가정하지 않는다.

### B 완료 검수

- 취업 사례는 ‘모델 응답을 비교·평가한 경험’으로 직무명이 다른 AI 평가 공고를 찾는지를 본다. 학위·전공·어학 점수·마감 조건의 판정도 함께 확인한다.
- 창업 사례는 같은 팀의 목표를 ‘시제품 제작비’에서 ‘판로 상담’으로 바꿨을 때 사람이 적합하다고 표시한 공고가 상위에 오는지를 본다. 지역·업력 미상은 확인 필요로 둔다.
- 같은 자료에서 **현행 규칙 / 키워드 추가 / 키워드+의미 검색**의 상위 3개 적합 공고 수를 분야별로 비교한다. 인용 정확도는 설명을 붙인 뒤 별도로 측정한다. 평가 세트에서 자격 오판 0건, 잘못된 공고·버전 인용 0건을 확인한다. 표본 수, 오답 사례, 응답 지연과 모델 호출 수도 보고한다. 개선이 확인된 분야부터 기본 추천에 반영한다. [기존 평가 계획 M2·M3·M4·M10](EVALUATION.md)을 활용한다.

## 코딩 모델의 첫 작업

1. **A1부터 시작한다.** 두 시연팀과 목표 변경 사례를 입력으로 만드는 테스트, 프로필·노드 계약, 첫 추천을 만드는 순수 함수를 함께 작성한다.
2. A2와 A3를 연결하고 두 팀의 실제 대화 입력, 생성된 첫 노드, 목표 변경 전후의 완료 ID를 보고한다. 이 시점까지 벡터 DB와 임베딩 의존성은 필요하지 않다.
3. A 검수 후 B1부터 시작한다. B3 검색 품질과 B5 설명 품질을 개별 결과로 보고한다. 사람이 검토할 정답이 없는 경우 측정값을 만들어 쓰지 않는다.

기본 회귀 명령은 Python 3.12의 `api`에서 `python -m pytest -q tests app/assistant`, `web`에서 `node --test tests/*.test.mjs`, `npx tsc --noEmit`, `npm run lint`, `npm run build`다. 브라우저 시연에서는 모델을 대역으로 사용한 결과와 실제 모델 응답을 구분해 기록한다.

이 작업의 푸시는 사용자가 직접 한다. 구현 인계 시 변경 파일, 검증 결과, 남은 데이터·배포 작업을 함께 전달한다.

## 2026-11-24 RAG 구현 상태

공개 공고의 최신 문단을 공고 ID·버전·문단 ID·본문 해시로 색인한다. 분류·검수 메모와 원문 확인 안내문, 제목·모집 기한을 반복하는 가공 문단은 근거에서 제외한다. 제목 메타데이터와 원문 인용은 화면에서 구분한다. 취업과 창업을 구분해 BM25 키워드 검색을 실행하며, 같은 모델·차원의 임베딩 캐시가 있으면 코사인 순위와 RRF로 합친다. 창업의 시제품·판로·대회 목표에는 해당 지원 내용이 확인되는 후보를 사용한다.

웹 상태에서 모집 기간·지원 자격·명시된 직무 연결을 반영한 목록을 계산해 홈·공고·트리·챗봇이 공유한다. 마감·조건 미충족 공고는 준비 참고에 표시한다. 성공한 빈 검색 결과와 검색 장애를 구분하며, 장애 때 기존 추천을 사용한다.

공고 상세의 ‘내 목표와 연결되는 근거 보기’와 개인 비서는 검색된 원문을 사용한다. 모델은 제공된 근거 ID를 선택한다. 서버는 현재 공고·버전·문단을 다시 대조해 확인된 인용과 링크를 표시한다. 키가 없거나 모델 응답이 유효하지 않으면 검색 문단을 직접 표시한다.

로컬에서 공개 창업 카탈로그를 공고 DB에 보완하고 색인을 재실행하는 명령은 다음과 같다. 기존 공고 ID는 보존한다.

```powershell
cd api
.\.venv\Scripts\python.exe -m app.career.opportunity_search --index --startup-catalog ../web/src/lib/data/startupCatalog.json
```

임베딩 캐시를 만들 때는 같은 셸에 GEMINI_API_KEY를 설정하고 아래 명령을 실행한다. 실패 전에 완료된 배치는 저장되며 재실행 때 재사용한다. 모델·차원을 변경하면 해당 설정으로 다시 색인한다.

```powershell
.\.venv\Scripts\python.exe -m app.career.opportunity_search --embed
```

기본 임베딩 설정은 CAREER_EMBEDDING_MODEL=gemini-embedding-001, CAREER_EMBEDDING_DIMENSIONS=768이다. 현재 벡터는 기존 공고 DB의 JSON 열에 저장하고 애플리케이션에서 코사인 유사도를 계산한다. pgvector 확장·SQL 벡터 인덱스의 운영 적용은 남아 있다. Gemini Embedding 2 설정에서는 작업 접두어를 사용한다. [Gemini 임베딩 문서](https://aistudio.google.com/docs/embeddings)

키 없는 환경의 실제 공고 검색·원문 표시와 임베딩·생성 모델 대역을 검증했다. 실제 모델 호출 품질과 PostgreSQL 환경의 벡터 검색 성능은 검증 전이다. 실제 공고에 대한 사람의 적합성 정답표가 없어 추천 개선율은 산출하지 않았다. 현재 공개 자료의 상당수는 마감되었거나 본문이 짧아 추가 원문 보완이 필요하다.

로컬 공개 색인은 공고 425건, 제목·원문 문단 698개다. ‘모델 응답 비교 평가 LLM’ 검색은 강남언니 Agent Evaluation 공고의 LLM-as-a-judge 평가 경험 원문을 찾았다. 이 공고는 모집 상태가 미확인이므로 준비 참고로 다룬다. ‘판로 상담’에 직접 대응하는 창업 원문은 현재 자료에 없어 해당 목표 검색 결과가 비어 있다. 두 목표에 각각 맞는 자료가 있을 때 후보가 바뀌는지는 고정 합성 공고와 브라우저에서 검증했다.
